# Roadmap Minecraft Launcher

> Исторический снимок согласованных планов; сохранён до согласованного удаления.
> Актуальный единый scope, критерии и приоритеты: [PROJECT_LEDGER.md](PROJECT_LEDGER.md).
> Этот файл больше не обновляется как отдельный roadmap. Правила агентов:
> [AGENTS.md](../AGENTS.md).

> Этот документ фиксирует согласованный объём будущих этапов. Планы не являются
> реализованными функциями. Текущая стабильная основа описана в
> [PROJECT_STATUS.md](PROJECT_STATUS.md).

## Подтверждённые факты

- Стабильная v0.6.0 опубликована и поддерживает основной запуск серверного профиля,
  pack sync/repair, profile file management и обновления приложения.
- Текущий Play всегда использует серверный адрес выбранного профиля.
- Настройка RAM уже существует и ограничивается политикой безопасного использования
  физической памяти.
- Текущее удаление касается только известных managed pack-файлов; пользовательские
  и общие Minecraft-данные сохраняются.
- Операции одного профиля защищены внутри процесса и между процессами Launcher.

## Согласованные требования

### v0.6.1 — ограниченное функциональное обновление

v0.6.1 должна содержать только два режима запуска, точный ввод RAM и небольшие
UX-исправления. Новые типы локальных сборок, полный storage manager и серверная
админка в неё не входят.

#### Два режима запуска Minecraft

Существующая основная кнопка остаётся серверным запуском:

- выбранный профиль синхронизируется;
- подготавливаются те же Minecraft, Fabric, моды, config и RAM;
- в launch arguments передаются адрес и порт сервера;
- сохраняются текущие process/profile locks и обработка ошибок.

Новая кнопка «Одиночная игра» должна:

- использовать тот же выбранный серверный профиль и тот же instance;
- выполнять обычный pack sync до запуска;
- использовать те же Minecraft, Fabric, моды, config, nickname и RAM;
- не передавать server address/port или quick-play server arguments;
- открывать главное меню Minecraft;
- участвовать в тех же блокировках Play/Repair/Delete/update;
- не создавать отдельную локальную сборку или отдельную schema профиля.

Минимальные проверки:

- launch request различается только намерением подключения;
- одиночный запуск не содержит server endpoint в CmlLib options;
- серверный запуск сохраняет текущее поведение;
- pack failure запрещает оба запуска;
- второй Launcher не запускает тот же профиль параллельно;
- cancellation и завершение процесса освобождают lock.

#### Точный ввод RAM

- Существующий ползунок сохраняется.
- Рядом добавляется числовое поле в мегабайтах.
- Ручной ввод поддерживает точность до 1 МБ.
- Значение, введённое вручную, не округляется до шага ползунка или 1024 МБ.
- Ползунок и поле синхронизируются без потери сохранённой точности.
- Применяются существующие безопасные ограничения по физической памяти.
- Точное значение сохраняется в текущем `settings.json` без изменения формата.
- Старые настройки загружаются без миграции и потери совместимости.
- Ошибочный, пустой и выходящий за границы ввод получает понятную валидацию.

Минимальные проверки:

- значения вроде 3073 МБ сохраняются и передаются в launch request без округления;
- границы RAM и недостаточная физическая память обрабатываются существующей policy;
- изменение ползунка даёт привычный дискретный шаг;
- reload settings восстанавливает точное ручное значение;
- keyboard input, focus и DPI не ухудшаются.

#### Небольшие UX-исправления

- Понятнее объяснить, какое действие заблокировано работающим Minecraft или другой
  операцией профиля.
- Показывать реальный update channel (`stable` или `dev`) из package/runtime state,
  не из server config.
- Улучшить пользовательские сообщения об ошибках, сохраняя технические подробности
  в локальном логе.
- Не добавлять фиктивные online, ping, player count или новые серверные данные.

#### Gate готовности v0.6.1

- Все существующие тесты проходят без регрессий, добавлены тесты новых launch modes
  и точного RAM.
- Server Protocol v1, Pack Manifest v1 и settings format не меняются.
- Выполнены ручные smoke tests обоих режимов запуска.
- Проверены RAM field, slider, restart и сохранение settings.
- Проверены installed update path и release feed для конкретной версии.

### v0.6.2 — безопасное управление дисковым пространством

Этот этап не смешивается с v0.6.1.

Требуется:

- показать объём данных выбранного профиля и отдельно общих данных;
- безопасно удалить установку выбранного профиля;
- по умолчанию сохранить `saves`, `screenshots`, пользовательские resourcepacks,
  shaderpacks, options и unmanaged mods;
- предложить отдельную, более опасную очистку общих `assets`, `libraries`, `versions`
  и managed Java;
- учитывать, что общие файлы могут использоваться несколькими профилями;
- запрещать удаление при запущенном Minecraft, sync, repair или конфликтующей операции;
- показывать точное подтверждение перед опасным действием;
- выполнять удаления только внутри проверенных корней, без следования через
  symlink/junction/reparse point;
- после удаления оставлять состояние, при котором следующий запуск корректно
  восстановит необходимые managed-файлы.

Минимальные проверки должны использовать только временные каталоги и охватывать
path traversal, reparse points, сохранение пользовательских данных, другие профили,
shared-file accounting, cancellation и повторную загрузку.

### Отдельный серверный трек

Pack Manager, управление модами Minecraft-сервера и административные интерфейсы
описаны в [PACK_MANAGER_PLAN.md](PACK_MANAGER_PLAN.md). Они не являются частью
v0.6.1 или v0.6.2 без отдельного решения.

## Приоритеты

1. Начать v0.6.1 с моделирования намерения запуска и тестов Core.
2. Реализовать одиночный запуск, не меняя pack sync и server schema.
3. Добавить точный RAM input и тесты persistence.
4. Выполнить ограниченную UX-полировку.
5. Выпустить и проверить v0.6.1.
6. Только затем проектировать storage inventory/removal v0.6.2.
7. Pack Manager вести отдельными design/implementation PR.

## Идеи и предложения

Следующие варианты требуют design review и не являются обязательными требованиями:

- Core enum/value object наподобие `GameLaunchMode.Server` / `Singleplayer`, чтобы
  UI не управлял CmlLib flags напрямую.
- Сохранять точное RAM как единственное числовое значение, а slider рассматривать
  как один из способов его изменения.
- Для v0.6.2 сначала создать read-only inventory service, а удаление добавить после
  проверки ownership-модели.
- Вести reference index общих runtime-файлов только если CmlLib и несколько профилей
  не позволяют безопасно вычислить использование на лету.

## Вопросы для проверки

### Перед v0.6.1

- Какой минимальный и максимальный RAM допускает текущая `RamPolicy`, и как поле
  должно объяснять clamp пользователю?
- Какие CmlLib options сейчас добавляют server address и port и достаточно ли их
  не задавать для открытия главного меню?
- Где компактнее разместить вторую кнопку без ухудшения компоновки 900×650?
- Как надёжно получить текущий Velopack channel в installed и development mode?
- Какие существующие сообщения блокировки следует разделить по Play, Repair и Delete?

### Перед v0.6.2

- Что считать «установкой профиля» помимо managed pack-файлов?
- Какие пользовательские config/options могут одновременно быть pack-managed?
- Можно ли достоверно определить пользователей общих versions/libraries/assets без
  собственной reference database?
- Нужен ли режим предварительного просмотра удаления со списком и размером файлов?
- Какая политика отката нужна при частично неуспешной очистке?

## Не делать сейчас

- Не реализовывать отдельные локальные/offline profiles.
- Не менять Server Protocol v1 или Pack Manifest v1 ради launch mode.
- Не добавлять SSH/SFTP или admin credentials в пользовательский Launcher.
- Не объединять app update и game pack update.
- Не начинать v0.6.2 до завершения scope v0.6.1.
- Не переносить production pack hosting без инвентаризации и резервной копии.
